# `.hdict` 私有词库容器与拼音词库

> 一句话：拼音词库从 8.2 万条明文 `py_table.txt` 换成 47.5 万条带词频的
> `py.hdict`（rime 字词库合并注音 → 统一码表行流 → raw deflate 压缩 → 定长头容器），
> 拼音/双拼共用这一份。

## 为什么要换

1. **老词库没词频**。8.2 万条 `候选\t连写全拼`，同码重码的次序只能靠文件序，而文件是按
   拼音字母排的 —— 「组织 / 阻止 / 阻滞 / 足趾」谁常用，表里答不出来。拼音侧的
   `ordinal`（重码序号）直接喂给解码器的轻罚与格子截断，次序错了等于打分错了。
2. **覆盖面**。老表 8.2 万条，收集的 rime 字词库去掉长尾后仍有 47.5 万条可用，
   同音词与词条的覆盖都厚了一个量级。
3. **体积**。词库要进 app 包随 pkg 分发：明文 26 MB 太大，`.hdict` 里 deflate 后 5.7 MB。

## 容器格式

定长头 64 字节 + 单个负载块；负载是统一码表格式的行流 `候选\t编码[\t词频]`
（UTF-8，`\n` 分隔）。写侧 `scripts/build_pinyin_hdict.py`，读侧 `Fire/Table/HDict.swift`，
字段偏移两边逐条对齐（小端）：

| 偏移 | 长度 | 字段 | 含义 |
|------|------|------|------|
| 0 | 4 | magic | `HDCT` |
| 4 | 2 | version | 容器版本 = 1 |
| 6 | 2 | kind | 1 = 拼音（编码列是连写全拼），2 = 双拼（预留） |
| 8 | 2 | codec | 0 = 原样，1 = raw deflate |
| 10 | 2 | flags | bit0 = 行带词频列，bit1 = 行已规范化且 `(词,码)` 已去重 |
| 12 | 4 | entry_count | 词条数 |
| 16 | 8 | payload_size | 解压后字节数 |
| 24 | 8 | stored_size | 容器内负载字节数 |
| 32 | 4 | payload_crc32 | 负载 CRC-32/IEEE |
| 36 | 4 | header_crc32 | 头部 CRC（计算时本字段与保留区按 0 计） |
| 40 | 24 | 保留 | 全 0 |

三个设计点：

- **压缩选 raw deflate**（Python `zlib wbits=-15`）：与 Apple `Compression` 框架的
  `COMPRESSION_ZLIB` 是同一种流，系统库一次 `compression_decode_buffer` 解完，
  不引第三方依赖，也不用改 TableBuilder（C++ 那侧维持「只读两列明文」）。
- **负载仍是行文本**：`.hdict` 只是容器 + 压缩 + 校验，不是新的数据模型。
  拼音音节索引、整句词图、sqlite 建表三条读路共用同一套「`候选\t编码[\t词频]`」解析，
  明文 txt 与容器只差一个 `HDict.tableText`。
- **flags 的「已规范化」声明**：写侧保证词面无空白、编码只用 `a-z`、`(词,码)` 已去重，
  读侧据此跳过逐行 trim 与去重集（47.5 万条下载入 2.29s → 1.85s）。手写表不打这个标记，
  照旧逐行校验。

校验分工：载入路径查 magic / 版本 / 头部 CRC / 声明长度 / inflate 结果长度 /
UTF-8 可解码，词条数与容器声明不一致就写日志；负载逐字节的 CRC32 只在
`--pinyin-selftest`（`HDict.verify`）与 `--verify`（Python）里跑 —— 那是十几 MB 的扫描，
不该塞进启动路径。

## 词库里的数据从哪来

`tmp/pinyin_dict/`（rime 格式 `词\t音节 音节…\t词频`，来自 rime-ice）：

| 文件 | 内容 | 默认档 |
|------|------|--------|
| `base.dict.yaml` | 基础词库 | 词频 ≥5 收录 |
| `ext.dict.yaml` | 扩充词库 | 词频 ≥5 收录 |
| `8105.dict.yaml` | 《通用规范汉字表》+ 25 亿语料字频 | 全量收录 |
| `tencent.dict.yaml` | 腾讯长尾（词频基本为 0） | 不进默认档 |
| `41448.dict.yaml` | 大字表（生僻字） | 不进默认档 |

处理规则：

1. **注音合法性以引擎的音节表为准**：脚本直接从 `Fire/Pinyin/PinyinSyllables.swift` 读
   `PinyinSyllables.all`（413 条），词库里出现引擎切不开的音节（`cei` / `yai` / `lvan` /
   `biang`…共 66 条）整条丢弃；`lue/nue` 按 `PinyinSyllables.canonical` 归一到 `lve/nve`。
   抄一份音节表到 Python 迟早和引擎漂开，所以不抄。
2. **编码写连写全拼**（`开发 → kaifa`）：与其余码表、TableBuilder 建 sqlite、
   混输的 `query glob` 前缀查询同一口径。音节切分仍由引擎在建索引时枚举
   （`xian` 进 `xian` 与 `xi an` 两个键，西安 / 先 都查得到）。
3. **多源按 `(词,码)` 去重**，词频取各源最大值；同词的不同读音各留一条（长 chang / zhang）。
4. **输出按「词频降序 → 词长升序 → 码 → 词」排序**。文件序在 Fire 里就是 rank，
   所以这个排序就是打分标定：同音词里常用的排在前，腾讯那批 0 频长尾自然沉底。

## 实测（同一份冻结句子集 2742 句，冷启动不学习）

| 敲法 | 旧 `py_table.txt` | 新 `py.hdict` |
|------|-------------------|----------------|
| 标准全拼 | 首选 42.9% / 字 85.8% | **首选 48.6% / 字 88.6%** |
| 小鹤 / 自然码双拼 | 43.5% / 86.2% | **49.4% / 88.9%** |
| 35% 音节只敲声母（简拼） | 17.0% / 63.8% | **20.7% / 67.4%** |
| 每句约 0.5 处相邻敲反 | 29.3% / 55.7% | **33.2% / 57.8%** |
| 平翘舌混敲（开模糊音） | 34.5% / 81.0% | **41.4% / 85.0%** |

代价与开销（M 系列，Release 口径；两列都是同一版引擎代码，逐键行为全量 96205 键的模拟，
每键从头重查一次）：

| 指标 | 旧 | 新 |
|------|----|----|
| 音节索引载入（后台） | 0.17s | 1.85s |
| 索引常驻（键 818K / 词目 935K） | 34 MB | ~200 MB（含建索引瞬时峰值） |
| 逐键模拟 p50 / p95 / p99 | 1.3 / 4.1 / 6.1 ms | 2.2 / 8.1 / 64.5 ms |
| 词库文件 | 1.09 MB 明文 | 5.96 MB 容器（负载 12.2 MB） |
| `建立索引`（sqlite） | ~5s | ~8s |
| 五笔拼音混输单键查询（最差档 `z…`） | 9.2 ms | 11.6 ms |

换词库时引擎里跟着改了两处，都是被大词库逼出来的：

1. **预选那一刀改成按词库常用度砍**（`PinyinEngine.rank` 里的 `dictRank`）。
   原先词库没频率，拿「模型从 BOS 走一遍的一元分」顶替，代价是每条候选都要跑一遍
   语言模型；四十多万条词库下一次查询命中上万条，逐键 p99 直接顶到 300ms。换回词库
   名次（`hit.rank`，只比整数）后：新词库 p99 300 → 64ms，旧词库 p99 28 → 6ms，
   首选命中率一点没动。`PinyinDecoder.wordPrior` 从此没人用，已删。
2. **截断时给「只覆盖输入前缀」的候选留尾巴**（`PinyinEngine.truncate`）。
   排序第 2 键是覆盖字母多者优先，词库一大，`kaif` 光「盖满四键」的两音节词就能占到
   60 个名额，「开」这种只吃掉 `kai`、等用户继续打或直接选字的字一条都进不了候选栏
   （自检「未打完的 kaif 也出前缀词」当场报红）。预选与出候选两刀都按覆盖长度分档留位。

两点说明：

- **混输只收最常用 15 万条**（`mixedInputDictRows`）。混输走 `wb_py_dict` 的
  `query glob 'xxx*'`，`group by text` 要聚合全部命中行，每一键的开销正比于
  「以这几个键开头的词条数」；全量进表时单字母查询从 2.7ms 顶到 32ms。拼音模式不受
  这一刀影响，它查 `.hdict` 建的音节索引。
- **逐键 p99 变胖是已知还没还的债**。音节索引从 6.9 万键推到 81.8 万键，而
  `PinyinLexicon.narrow` 的收窄就是「按键做字符串比较 + `key.index(offsetBy:)` 取后缀」，
  每键查询扫过的键数随词库线性涨（同一批 900 句的逐键模拟：core / standard 的 p99 分别是
  32 / 62ms，索引键数 40.7 万 / 81.8 万）。把格子候选、beam、简拼回溯、每键同音深度全收到
  8 / 16 / 3 / 128 条，p99 纹丝不动 —— 说明钱花在收窄本身，不在候选规模。
  下一步该把索引换成字节/整数键（或只按词的**真实**音节切分建键，键数能砍掉四成），
  而不是继续调候选上限。想要旧手感：`--tier core` 重生成（首选 47.7%，p99 回到 30ms 量级）。

## 重新生成词库

```bash
# 默认档（standard：base≥5 + ext≥5 + 8105）→ Fire/Resources/schemas/py.hdict
python3 scripts/build_pinyin_hdict.py

# 体检：magic / 版本 / 头部 CRC / 负载 CRC / 长度 / 词条数逐项核对
python3 scripts/build_pinyin_hdict.py --verify Fire/Resources/schemas/py.hdict

# 换档：core 更轻（27 万条），full 全量（99 万条，实测首选反而略降、逐键更慢）
python3 scripts/build_pinyin_hdict.py --tier core --out /tmp/py_core.hdict
python3 scripts/build_pinyin_hdict.py --tier full  --plain /tmp/py_full.txt

# 手工挑源与准入词频
python3 scripts/build_pinyin_hdict.py \
  --sources base.dict.yaml:5,ext.dict.yaml:5,8105.dict.yaml:0 --out /tmp/py_custom.hdict
```

改完词库要在 app 里「词库 → 建立索引」重建 sqlite 混输索引；音节索引由
`PinyinEngineCenter` 在换 `pyTablePath` 时自动重建。

档位实测（首选/字是全量 2742 句；载入与逐键 p99 取同一批 900 句的模拟，只用于横向比较）：

| 档 | 词条 | 首选 / 字 | 载入 | 逐键 p99 |
|----|------|-----------|------|----------|
| core | 270,055 | 47.7% / 88.2% | 1.1s | 32 ms |
| **standard（默认）** | **475,342** | **48.6% / 88.6%** | **1.9s** | **62 ms** |
| full | 992,524 | 48.2% / 88.4% | 5.0s | — |

`--tier full` 里 `tencent`（0 频长尾）与 `41448`（生僻字）都是负收益或零收益：
长尾同音词把格子里的常用词挤掉，实测首选 48.6% → 48.2%；只加 `41448` 更是掉到 47.8%
（同一个字的第二读音被大量生僻字撑开，重码变深）。所以默认档停在 base+ext+8105。

## 换成明文码表 / 回退

「偏好设置 → 词库 → 拼音词库」点路径可以挑任何 `.hdict` 或明文
`候选\t连写全拼[\t词频]` 的 txt（选 `.hdict` 时先验容器头，读不出直接弹回）。
词库面板上会显示容器的词条数与压缩比。
